# 1DM+ 18.2: filter storage and matching investigation

Investigated on 24 October 2026 using REA 6.7.0 and its JADX 0.7.1 provider.

The supplied replacement archive is complete. The inspected code confirms two storage layers: a compressed source file for each list, and separate binary files containing the combined matcher and its indexes. The request matcher uses the loaded indexes; the ZIP files are read when source lists need parsing. Compression can save disk space, while the compiled indexes and matching shortcuts explain how the architecture avoids repeated expensive work. Their actual speed and memory advantage was not measured on a running device.

## 1. Per-list source storage: ZIP confirmed

**Observed:** `i.Ok.m7168` opens the selected source's saved local path, wraps its input stream in `ZipInputStream`, selects an entry, wraps that in `InputStreamReader` and `BufferedReader`, and processes `readLine()` results. Thus it does not first inflate the complete list into a single String in this path.

The downloader `idm.internet.download.manager.e.m16524` contains `ZipOutputStream`, `ZipEntry`, and repeated input/read-to-output/write operations. A network-response branch uses a UUID-named temporary file, finishes/closes the ZIP, and then replaces the destination through its file abstraction. The method falls back to **smali** in REA, so its bytecode is the basis for these observations; it is not reliable reconstructed Java control flow. The visible copy buffer is 0x2000, or 8 KiB. It puts a numeric length value in the entry comment; `CheckAppVersion.m14522` reads the first entry's comment as a length value.

The source record supplies the cache pathname. `i.o1.m12467` resolves `{{internal}}` and `{{external}}` placeholders; this does not establish one universal source-cache directory for all installations. The ZIP content format is confirmed independently of the cache filename's extension.

## 3. Combined binary caches: indexes survive restarts

**Observed:** `i.Ok.m7151` reads these files under Android `Context.getFilesDir()`:

| File | Observed payload |
| --- | --- |
| `abnfp.bin` | Network-rule count/flags and five serialized network indexes, restored through `i.nJ.m12341` |
| `abnhp.bin` | Hosts-related data, restored into a set of integer hashes |
| `abcfp.bin` | Cosmetic-rule count and serialized cosmetic engine, restored through `i.vc.m13893` |

`i.Ok.m7170`, `m7169`, and `m7167` write the corresponding files. The network serializer writes rule indexes through a custom byte-buffer writer, not Java `ObjectOutputStream`. `i.yQ.m14185` restores the rule records **and the integer lookup/index arrays**. This is a material distinction from a cache that saves rule records but reconstructs all token buckets at every startup.

`i.Ok.m7151` reads files into byte arrays and reconstructs Java data structures in the inspected path. This path does not demonstrate memory-mapped or native-only matching. Decompilation includes duplicated/unreliable branches in `m7151`; its filenames, reads, deserializers, and readiness flags are visible, but precise fallback branch ordering is not fully established.

## 4. Requests select candidates through token indexes

**Observed:** the `i.yQ` constructor receives each rule's token groups. It builds a token-frequency histogram, chooses a relatively rare token from each group using that histogram, and builds bucket offsets plus token/rule-index pairs. The histogram uses modulo buckets, so this is an approximate frequency selection, not proof of exact global token frequencies.

At request time, `i.bQ.m10336` lazily computes and retains an integer token array. `i.nJ.m12347` passes those tokens to `i.yQ.m14190`, which looks up matching buckets through `m14189` and invokes the actual rule predicate. A token hit is only a candidate; `i.nJ.m12351` still calls `i.iJ.m11450` to check the rule.

`m14189` also caches materialized token buckets in a `ConcurrentHashMap`, uses a request generation marker to avoid processing a bucket twice in one lookup, and promotes a successful candidate one position within its bucket. The inspected class does not show a bound on that map. Any adaptation in Miowser should retain explicit memory bounds.

The hosts path has an earlier integer-hash set lookup in `i.Ok.m7157`. That is cheaper than evaluating URL-pattern rules for every request, but adopting hash-only decisions needs separate correctness analysis; the present investigation is not a proof of collision-free decisions.

## 5. Simple matching avoids regex work

**Observed:** `i.iJ.m11406` has direct equality, suffix, substring, and anchored-string checks, with separate domain handling. It calls a compiled pattern only for rules requiring that branch.

`i.iJ.m11446` lazily compiles a pattern and retains it on that rule. The binary reader `m11391` restores pattern text/options and passes a null compiled pattern to the constructor. Loading the cache therefore does not eagerly compile every rule's regex in this path.

## 6. Refreshing and rebuilding are separate activities

**Observed:** `CheckAppVersion.m14526` iterates the selected source records and invokes the downloader separately for each. It tracks whether sources changed or compiled files are absent; its rebuild branch collects enabled sources whose cached paths exist and calls `new Ok(null).m7171(...)` to rebuild the combined files, followed by an adblock-refresh broadcast.

The parser distinguishes hosts, network, and cosmetic lines. It deduplicates network/cosmetic rules using integer identities in a shared set across processed sources. The temporary builder clears source lists/index data after serialization. This shows explicit release of builder collections; it does not prove that the app can never run out of memory.

The visible source-update method and ZIP comment reader support change/status metadata, but a complete HTTP conditional-request policy, including ETag/304 behavior, was not established. The downloader's Java decompilation failed and its relevant stream operations were checked in smali.

| Memory | Streams source files, uses compact identities and binary representation; still allocates Java collections and file-sized byte arrays | Streams sources, avoids parsed-list duplication, checks heap headroom | Continue measuring build/load peaks; retain bounded caches and exact rule verification |

Relevant local files: `FilterSubscriptionStore.kt`, `AdBlockFilters.kt`, `FilterEngine.kt`, `FilterTokenIndex.kt`, `FilterRule.kt`, and `CompiledFilterSnapshot.kt` under `app/src/main/java/com/miowser/app/adblock/`.

Each matcher change needs comparison tests covering exceptions, manual-rule precedence, domains, case handling, separators, and resource types. This investigation does not implement those changes.
