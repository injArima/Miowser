## Run the measurements

1. Connect only the intended device. Use `adb devices` to get its serial. The runner refuses ambiguous device selection.
2. Close other profiling tools and heavy host workloads. For shipping measurements choose a physical midrange phone, then repeat on a low-memory phone. Record thermal conditions and keep OS, WebView, refresh rate, power settings, and fixture parameters constant.
3. Run the unminified baseline first:

   ```powershell
   ./scripts/Run-OptimizationBenchmarks.ps1 -Serial DEVICE_SERIAL -Journey populatedStartup -Iterations 20 -Tabs 10
   ./scripts/Run-OptimizationBenchmarks.ps1 -Serial DEVICE_SERIAL -Journey all -Iterations 20 -Tabs 10
   ```

4. Repeat startup with `-Tabs 1` and `-Tabs 30`. Repeat Downloads scrolling with `-Downloads 1000` for the stress case. Default is 200 download records.
5. Compare R8 separately, using identical parameters and `-R8`. Keep both APKs and their hashes. Both configurations use `CompilationMode.None()` to hold compilation policy constant; these scores do not claim the benefit of an installed Baseline Profile.
   After generating and packaging profiles, use `-R8 -Compilation BaselineProfile` for a separate profile-enabled measurement. This requires successful profile installation and uses zero warmup iterations. Do not mix that compilation policy into the R8-only comparison.
6. For the disposable emulator use `-Serial emulator-5580 -EmulatorDiagnostic`. This explicitly suppresses only Macrobenchmark's emulator check. Treat its numbers as harness diagnostics, never physical-device acceptance.
7. Inspect JSON metrics and per-iteration Perfetto traces in the timestamped `.local/optimization/evidence/step03` directory. It also contains environment data, Gradle output, APK/hash, and the tracked working-tree patch. The runner captures a source checkpoint including new files and saves R8 mappings for optimized runs.
8. Run `./scripts/Summarize-OptimizationBenchmarks.ps1 -EvidenceDirectory PATH` to extract startup medians, nearest-rank p95, sample counts, frame-distribution percentiles, and positive frame-overrun counts/percentages into CSV files. The runner also saves before/after battery and thermal records, plus power-saving, locale, and font-scale settings.

## What each journey measures

| Journey | Measured work | Readiness condition |
|---|---|---|
| populatedStartup | Cold start, 20 repetitions by default; initial and fully-drawn timing | Library grid and first fixture card; fully-drawn signal waits for index/settings/session restoration |
| libraryScroll | Three downward and upward flings; frame timing | Populated Library grid |
| downloadsScroll | Three downward and upward flings; frame timing | Populated unfinished-download list |
| browserAndTabs | Enter browser, open tab overview, activate a tab; frame timing | Browser controls and tab grid/card |
| localPlayer | Open the playable fixture; frame timing | Media3's rendered-first-frame callback |

Frame timing for a journey is not the same metric as action-to-first-response latency. Inspect its trace before comparing with the separate interaction-latency targets in the plan. First-frame readiness is not a comprehensive player compatibility test.

## Fixture contract: synthetic-v1

- 500 Library entries, 2,000 History records, 200 or 1,000 failed download records, and 1/10/30 embedded HTML tabs. Each page invokes the real cosmetic, media-grabber, and renderer-download JavaScript bridges with harmless inputs and displays a success marker. Inspect that marker visually after shrinking: the current stacked WebView host does not expose its page descendants to UI Automator. The automated browser journey verifies the native tab overview and activation instead.
- Fixed record timestamps and deterministic names. Failed download records cannot start network jobs. History URLs use the reserved `.invalid` domain. Browser tabs do not depend on public network services.
- The first Library record points to a bundled three-second MP4 copied to app-private storage. It was generated by recording the dedicated disposable emulator at 320×720. The other entries are metadata-only placeholders; this fixture measures list/index cost and does not model 500 decoded artworks or real media files.
- The seed Activity runs in a separate process, writes through the existing codecs, commits before announcing readiness, and is killed before measurement. It never runs in the timed startup interval. Each test reseeds the indexes.
- Before each cold iteration, the runner cancels this benchmark package's scheduled jobs, including the API 34+ WorkManager namespace, outside the timed region. This prevents a pending filter-refresh job from rebinding while the previous process is being stopped. The measured launch still executes normal initialization and schedules its normal work. This controlled cold-start scenario is distinct from measuring concurrent background refresh.
- These datasets do not cover active transfers, remote streaming, hostile sites, or renderer memory pressure. Keep those release gates separate.

## Baseline Profile generation

Run `./scripts/Run-OptimizationBenchmarks.ps1 -Serial DEVICE_SERIAL -Journey profile`. This uses `BaselineProfileRule` directly in the same self-instrumenting module and archives generated text profiles. API 33+ supports collection without root. The generator currently targets populated startup. Use the unminified variant, then run `./scripts/Update-OptimizationProfile.ps1 -EvidenceDirectory PATH` to merge profile rules, exclude benchmark-only fixture classes, and place the baseline/startup profiles in `app/src/main`. Build release and verify `assets/dexopt/baseline.prof` before claiming profile delivery.

The module was configured in source using the official direct-module route rather than interacting with Android Studio's template UI. Automatic profile installation/generation is not implied by merely adding the generator class.
